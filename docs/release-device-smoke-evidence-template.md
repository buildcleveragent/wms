## 核验候选 APK

领取本次冻结源码的发布构建记录、签名 APK 和发布方登记的证书指纹。按每个 APK 各填一份身份记录。
本仓库的 `wmspda/manifest.json` 声明 `__UNI__5BF0B35`、`1.0.0/100` 及 `TH-PlatformSDK`。
`wmsandroid/manifest.json` 声明手机端 `__UNI__E10A49B`、`1.0.1/101` 和包名
`com.jinqiaorongtong.wmsandroid`。同一版本号可对应多次构建，以冻结构建记录中的 SHA-256 核对。
`wmspda/unpackage/release/apk/` 下文件名带 `20260421` 的旧包和 `unpackage/debug/` 中的调试
基座缺少本次收货修改的构建记录。

在带 Android SDK Build Tools 的验收机，将 `APK` 设为候选文件路径，`DEVICE` 设为本台测试机
的 ADB 设备编号。保留命令输出，逐项比对 APK 哈希、签名证书指纹和包名版本。签名校验失败或
与发布记录不符时停止安装并记录差异。

```sh
sha256sum "$APK"
apksigner verify --verbose --print-certs "$APK"
aapt dump badging "$APK" | head -n 1
```

确认一致后在专用验收设备安装。将 `PACKAGE` 设为上一步从 APK 读到的包名，保存安装结果、
设备中实际版本以及连至验收后端的首次登录记录。

```sh
adb -s "$DEVICE" install -r "$APK"
adb -s "$DEVICE" shell dumpsys package "$PACKAGE" | grep -E 'version(Name|Code)='
```

## PDA 逐件序列号收货

至少在两台现场配发的 PDA 上按实际扫码配置逐台执行。每台使用独立的合成任务和未登记过的
两个序列号。登录仓库操作员，从首页「收货(有订单)」领取并开始一个普通收货任务，选择允许的
收货库位。准备一条计划 2 件的序列号商品行和一条计划 3 件的普通商品行，另备一张有两条
序列号商品行的任务供切换焦点测试。此入口对应
`POST /api/inbound/pda/tasks/<task_id>/record-receipt/`。分批验收任务使用独立流程。

在 `wmspda` 有订单收货页点击目标行的「本件序列号」，用物理扳机读取打印标签。键盘输出
支持 Enter 提交。广播输出使用 `android.intent.ACTION_DECODE_DATA` 的 `barcode_string` 字段，
只回填聚焦的空序列号框。核对后点击该行提交按钮。扫错时点击「清除重扫」，再点输入框扫码。
在现场使用的每种输出模式下记录下表的结果，并在商品搜索页验证原生扫码生命周期。若目标机型
采用其他广播协议或扫描值无法送入正确行，记录具体机型、输出配置和阻断状态。普通 Android 手机的
`wmsandroid` 使用摄像头，当前有订单收货页提交体没有 `serial_no`。手机和 PDA 的实测结果
分别登记。[PDA 扫描生命周期](../wmspda/docs/android-scanner-acceptance.md) · [手机摄像头场景](../wmsandroid/docs/android-scanner-acceptance.md)

| 操作 | 可复核的通过条件 | 实际、结果与证据路径 |
| --- | --- | --- |
| 选好库位，留空序列号并点击「登记本件」 | 提示「请扫描或输入本件序列号」，收货请求数为 0 | |
| 用广播模式在另一条序列号行、普通数量框、库位弹层、隐藏页面之间切换并实扫 | 只有当前聚焦的可编辑序列号框收到扫描。首个广播只回填，连续广播不覆盖待确认条码。切回原页须重新聚焦，后台无额外收货请求 | |
| 实扫第一张标签并提交。在隔离测试网通过测试代理转发请求，确认后端已提交后让客户端收不到该次响应 | 保留代理时间戳和后台成功记录。请求属于正确任务行、货主、库位，包含 `serial_no`、`qty_ok=1`、`qty_damage=qty_reject=0`、`finalize=false` 和请求 ID。终端仍显示原序列号 | |
| 恢复网络，留在原页面并原样点击「登记本件」一次 | 两个请求的 `request_id` 及业务字段完全相同。第二个响应 `idempotent=true`，终端提示「已确认此前收货记录」。该行累计 1，序列号框清空，库位和已填批次保留 | |
| 再实扫第一张标签，使客户端发起新请求 | 服务端明确拒绝重复序列号，数量仍为 1 | |
| 清空刚被拒绝的序列号，聚焦输入框，实扫第二张标签。广播模式点「保存并结束该行」，键盘模式可用 Enter | 新序列号、新 `request_id`、`finalize=true`。该行累计 2，待处理 0，行已完成 | |
| 普通商品行按计划登记 3 件 | 显示数量输入，提交体没有 `serial_no`。该行累计 3 | |
| 后台复核原任务与日志 | 查询原任务、原行、正确货主和仓库。序列号行恰有两条 `TaskScanLog` 成功记录，各含唯一序列号、`code_type=SERIAL`、`qty_base_delta=1`。每个最终成功的序列号各对应一条 `inbound.receive.record` 审计，重放和拒绝均未增加成功行 | |
| 按仓库流程完成收货审核与过账，核对派生的上架任务，再执行上架审核过账 | 收货过账后，原任务的 `RECEIVE` 库存流水中两个序列号各增 1，派生上架行能追溯到各自流水且保留序列号。上架过账后核对目标库位、序列号、每件数量与库内合计，保存前后库存明细和流水编号 | |

记录设备、任务 ID、行 ID、库位、脱敏序列号、各次请求 ID、请求时间、状态码和重放结果。
保存带时间的终端录像及对应的脱敏服务端日志片段。失响应后须保持原页面，
确认原行输入已锁定，再次提交原内容。若首次请求未到服务器，重新准备任务，
重做「服务端已提交、终端未收到响应」场景。
