# POS 使用手册

- 版本：V2.1
- 业务基线：2026-09-07 当前工作区，包含未提交修改。
- 适用人员：门店收银员、仓库管理员；技术附录供实施与接口维护人员使用。
- 基线记录：[WMS 角色手册业务基线](manuals/BASELINE.md)。通用登录、账号范围与异常处理见[角色手册索引](manuals/README.md)。

本文根据页面、后端权限与业务代码、现有测试契约静态核对编写。描述代码支持的操作，不代表现场支付设备、打印机或部署环境已完成验收。金额、客户和单号示例均为合成数据。

## 1. 功能概述

POS 支持开班、扫码与商品搜索、购物车数量和议价、客户新增、单一或拆分收款、赊账、客户还款、整单作废、部分或全部退货、交班、销售报表及打印。结账成功会生成销售单，按商品货主拆分销售出库单，按先到期先出（FEFO）扣减可售库存，并写入库存流水。

POS 是即时销售流程。商品交付和实物退回应与系统记录一致；仓管可按销售单关联的出库记录核对库存，不要再对同一笔 POS 销售执行普通出库扣账。

微信、支付宝、银行卡等选项用于**记录现场已确认的收款或退款方式**，当前 POS 未接入这些通道的联机支付确认。系统保存“已收款”或“已退款”记录不等于资金已通过支付通道结算。销售单和交班单支持生成打印页面，物理出纸仍依赖浏览器、操作系统和现场设备；系统没有通用物理打印机驱动或打印队列。换货应先按退货流程处理原单，再确认新销售，不能把换货理解为自动抵扣的新交易。

## 2. 使用前准备

**前提**：账号已启用并绑定当前营业仓库，管理员已授予相应 POS 权限。POS 不要求收银员绑定货主；同一销售可以包含多个货主的商品。配置了显式角色范围的账号，其有效授权范围必须包含绑定仓库；系统保留未配置显式角色范围的旧收银员仓库绑定兼容路径，新增账号应按当前角色授权规范配置。

**入口**：登录仓库 PDA，从首页进入“POS收银”。经营查询从“POS销售报表”或“POS数据对账”进入。能看到按钮不表示拥有执行权限，最终以服务端校验为准。

**步骤**：

1. 确认登录人员、当前仓库和交接责任，完成上一位收银员的未决销售、还款与交班核对。
2. 确认商品已启用，商品编码、有效条码、销售单位和价格规则已维护。
3. 确认拣货区有可售库存。当前 PDA POS 按绑定仓库的拣货区查询并结账；存储区有货并不表示 POS 当下可售，应由仓管按补货流程处理。
4. 确认需要赊账的客户已在本仓库 POS 客户中启用，现场收款工具与打印配置可用。

**成功结果**：能查询当前仓库商品和客户，进入“当前班次”区域准备开班。

**异常处理**：缺少收银/查看权限、仓库未绑定或授权范围不一致时，交管理员核对账号配置；不要用其他人的账号继续结账。登录失效时重新登录原账号，再核对原交易结果。切换账号或仓库之前先处理结果不确定的交易；原账号的还款恢复记录不会转移给另一位收银员。

### 2.1 权限和岗位交接

| 操作 | 最低业务权限或条件 | 使用提示 |
| --- | --- | --- |
| 查商品、查/新增/更新 POS 客户、开班、结账、本人交班 | POS 收银权限；绑定仓库与授权一致 | 使用 POS 销售单新增权限，具体权限代码见附录 |
| 看销售、欠款、还款记录、报表、对账与打印/导出 | POS 销售单查看权限；绑定仓库 | 查询以绑定仓库为范围，不是跨仓总账 |
| 记录客户还款 | POS 客户还款权限或 POS 收银权限；新还款需本人进行中班次 | 页面查询欠款还需查看权限 |
| 提交退货 | POS 退货与退款两项权限；本人进行中班次 | 页面加载原销售还需查看权限 |
| 作废销售、主管重开班次 | POS 销售单修改权限 | 作废另受已交班、已有退货和已有客户还款限制 |
| 后台维护 POS 客户 | 后台登录权限及相应 POS 客户模型权限 | 与收银页面的客户维护授权路径不同 |

班次状态为“进行中”“已交班”或“已重开”。只有进行中或已重开的本人班次可以新结账、记录新还款及退货；交班只能交接当前收银员自己的班次。

## 3. 开班与登录交接

**前提**：使用本人账号，绑定仓库正确；现金备用金已经实际清点。

**入口**：“POS收银”顶部 → “当前班次”。

**步骤**：没有进行中班次时，在“备用金”输入框填写实际备用金并点击“开班”。已有班次时点击“刷新”，核对班次号、收银员、开班时间和当前汇总；同一收银员在同一仓库不能重复开两个进行中班次。

**成功结果**：页面显示班次号及进行中状态，结账按钮在购物车与支付信息合格后可用。备用金计入现金应点金额，不计入销售额。

**异常处理**：提示“请先开班”时先刷新班次。开班请求超时后也应先刷新，不要反复提交；若已有进行中班次，继续核对该班次。需要换人操作时，由原收银员完成交班，再退出并由接班人员登录、开班。

## 4. POS 客户管理与累计欠款

**前提**：客户归属本次收银仓库。POS 客户是本仓库独立客户档案，不需要先建立货主基础客户。

**入口**：“POS收银” → “客户信息”。

**步骤**：

1. 输入客户名称、编号或联系方式搜索并选择；核对姓名、电话、地址，避免同名客户混用。
2. 新客户点击“新增”，填写必填的客户名称，以及电话、地址，再保存。页面未要求输入客户编号时由系统生成。
3. 选择后核对“累计欠款”。普通现结可不选客户，以散客成交；需要赊账时必须选择启用的 POS 客户。
4. 需要修改完整档案或停用客户时，由具有权限的人员在后台“POS客户管理”处理；同一仓库客户编号不能重复。

**成功结果**：选中的客户绑定本笔 POS 销售，小票显示该客户；新增客户可直接使用。累计欠款按**当前仓库、该 POS 客户**计算，为有效赊账销售减去赊账退货冲减、再减有效还款，不是某一张销售单的未付款金额，也不跨仓合并。

**异常处理**：查不到客户时，先核对仓库、搜索词和启用状态，避免重复建档。若页面仍显示“已选客户仅用于同货主订单”的提示，该文字是遗留提示：当前选择的是独立 POS 客户，适用于整笔 POS 销售及客户欠款；底层按货主生成的出库单使用各货主自己的散客基础客户，不能据该提示重新选择其他货主客户。

## 5. 商品查询与购物车

### 5.1 扫码和搜索

**前提**：商品及相关标识有效，当前仓库存在商品库存记录。

**入口**：“POS收银” → 商品输入框、“扫码”或“搜索”。

**步骤**：扫描条码，或输入商品名称、规格、货主商品编码、仓库 SKU 编码等搜索；有多个结果时核对名称、规格、单位和可售数量，点击“加入”。每次扫码后检查最近扫码反馈及购物车数量。

**成功结果**：商品进入购物车，并显示当前拣货区可售库存、销售单位与换算后的基本数量。“无货”商品不能直接加入销售。

**异常处理**：未找到商品时，检查条码是否录错、商品/包装是否停用以及标识有效期。不要把商品尚在存储区误判为全仓缺货；交仓管核对库区及补货。反复扫描前先看购物车数量，避免按多次扫码意外增加数量。

当前扫码使用统一商品标识注册表，支持货主商品编码、仓库 SKU、GTIN/EAN/UPC、零码、箱码、其他条码、包装条码以及各来源系统的有效外部商品编码。历史条码记录只有仍启用、未删除、在有效期内且关联商品/包装有效时才可命中；停用、过期或尚未生效的标识不可用，其历史记录及编码占用仍保留。

箱码和包装条码按标识创建时固化的单位与基本数量换算。因此，新旧箱规同时有效时可以扫码到同一商品，但各自保留原箱规；不能按现行新箱规重新解释旧箱码。

### 5.2 数量、单位、单价和议价金额

**前提**：购物车有商品，已核对实际交付数量及销售单位。

**入口**：“购物车”中的“单位”“数量”“单价”“金额”。

**步骤**：选择销售单位并输入数量，检查同时显示的基本数量；需要议价时调整单价或金额，结束输入后检查系统换算结果、行金额及整单合计。

**成功结果**：提交以基本单位数量和四位小数基本单位成交价为准，行金额保留两位小数。明确输入的行金额是本行最终金额，成交价必须与“金额 ÷ 基本数量”四舍五入到四位小数一致。非零价销售同时受最低成交价与最高折扣限制；同一商品多行时会合计校验可售数量。

**异常处理**：数量、单价或金额校验不通过时，在原购物车修正后重新检查；不能用改包装单位绕过库存或最低价限制。当前代码允许数量为正、金额和单价均为零的赠品行及全赠品单；赠品仍扣库存，应依门店授权使用，不能用零金额绕过正常议价管理。

## 6. 收银结账

**前提**：本人班次进行中，购物车已核对，现场付款事实已确认；有赊账部分时已选客户。

**入口**：“POS收银” → 收款区域 → “结账”。

**步骤**：

1. 确认商品、单位、基本数量、金额、客户和备注；有外部小票号时填写唯一单号，不填由系统生成。
2. 单一付款选择现金、微信、支付宝、银行卡、赊账或其他方式；现金填写实际收到的金额，核对找零；非现金按本单应收记录。
3. 使用“拆分支付”时，逐行填写支付方式、“抵扣”金额、“实收”与可选参考号。各行抵扣合计必须等于应收；现金实收可以高于现金抵扣并产生找零，其他实际收款方式实收必须等于抵扣，赊账行实收必须为零。
4. 需要打印时选择打印配置并勾选“自动打印销售单”，再次核对后提交。
5. 等待结账结果，核对最近小票、销售单号及销售历史。

**成功结果**：显示“结账成功”，生成 POS 销售单、付款汇总及付款明细；跨货主商品生成多张关联销售出库单，库存按先到期先出规则扣减。成功后购物车重置，页面刷新班次和销售历史。小票同时展示本单赊账、累计欠款、实收及找零。

**异常处理**：库存不足、价格不合规、未开班、客户无效或支付不平时不会完成本笔销售，按错误修正后再核对。结账响应超时、登录变化或网络中断时，先在原仓库查销售历史、小票号与付款记录；**不要再次向客户收钱，也不要清空原单重新建单**。确认仍需恢复提交时保持原客户、商品、金额、支付方式和原请求标识不变；提示“同一幂等键对应的收银内容不一致”时先查原交易，不要直接换键重试。

合成示例：应收 100.00 元，现金抵扣 20.00 元、现金实收 30.00 元，微信抵扣及实收 50.00 元，赊账抵扣 30.00 元、实收 0.00 元。应找零 10.00 元，客户累计欠款增加 30.00 元。系统记录微信 50.00 元并不代替现场支付结果核实。

### 6.1 结账成功但打印失败

“结账成功，但自动打印失败”只表示打印后续步骤失败。先确认销售已在历史中，再从最近小票点击“打印销售单”或从原销售记录补打。不要再次结账。提示“结账成功，回执处理异常，请从销售历史查看”时，也按已成交核对原销售记录。

## 7. 客户还款与原请求恢复

**前提**：原仓库、原客户的累计欠款大于零；记录新还款时本人班次进行中。还款是客户账户级结算，不分配到某一张销售单。

**入口**：“客户信息”选择客户 → “累计欠款”下方的还款区域。

**步骤**：

1. 核对客户、欠款和收款凭证，选择非赊账的还款方式。
2. 输入大于零且不超过累计欠款的金额；“全额”使用当前显示欠款，提交前再次核对。
3. 填写可选参考号，点击还款按钮，核对确认框的客户和金额后记录收款。
4. 成功后核对欠款余额和当前班次的客户还款金额；需要追溯时由有查看权限的人员查还款记录。

**成功结果**：生成还款单，累计欠款减少，金额计入实际处理还款的班次和相应付款方式。还款不是新增销售，不增加销售额。

**异常处理**：

- 还款超时或响应不确定时，前端会保留原请求及固定请求标识。保持原账号、仓库、客户和浏览器数据，先核对原记录；不要把客户再次付款当成恢复请求的前提。
- 需要恢复时回到原客户再点击还款，页面优先复用原请求的金额、方式和参考号，确认框金额可能不同于后来修改的输入值。不得切换客户或修改金额后冒充原还款提交。
- 客户已无欠款、页面按钮不可用或原班次/账号状态妨碍恢复时，交管理员按原还款记录和参考号核对，不能为了重试新增欠款或重收款。
- 欠款已被另一位收银员更新时，以服务端余额为准；超额还款会被拒绝。原请求内容不一致、旧参考号已存在时，先核对历史，禁止换一个新参考号把同笔款项再记一遍。

## 8. 部分退货、全部退货与整单作废

### 8.1 退货并记录退款

**前提**：原销售已完成，仍有可退数量；当前操作人有退货及退款权限，且本人当前班次进行中。原销售所在班次已经交班时，仍可在当前班次处理符合条件的退货。

**入口**：“销售历史”或最近销售记录 → 对应销售单“退货”。

**步骤**：

1. 打开原单，核对货品实物与销售明细中“可退数量”。
2. 按需输入部分或全部退货数量，未退商品保持空白；页面退货数量以原销售基本单位为准，不按原包装箱数填写。
3. 填写必填退货原因，核对系统分摊的退货金额，选择实际退款方式及可选参考号。
4. 核对退款金额等于本次退货金额后确认。现有页面一次选择一种退款方式；接口支持多条退款明细，复杂的混合资金与赊账冲减由管理人员按实际金额处理。

**成功结果**：生成退货单及退款记录，库存按原销售实际扣减层回补，剩余可退数量、销售报表和当前班次退货汇总更新。原销售保持“已完成”，不因退完自动变成“已作废”。

**金额规则**：议价行按原行最终金额累计分摊，不使用当前售价重新定价。最后一次退完吸收分币尾差。示例：原基本数量 3、原行金额 10.00 元，分三次各退 1，退款分别为 3.33、3.34、3.33 元，累计恰好 10.00 元。

**异常处理**：

- 可退数量不足、退款金额不符或缺少原因时，刷新原单后修正。原库存层缺失或被软删除时，交仓管核查来源，不能另建一笔手工入库代替系统退货。
- 对赊账客户选择“赊账”退款表示冲减欠款，不是实际付出现金；冲减不能超过当前未还欠款。已还款部分需要按实际退款方式处理。
- 当前页面每次点击确认会生成新的退货请求标识，不能把界面再次点击视为可靠的原请求恢复。响应超时后先查退货记录、剩余可退数量和库存回补情况，再决定后续操作；不要重复退货或退款。
- 零金额赠品退货在后端支持空退款明细，但当前页面会提交一条退款明细，可能被零金额校验拒绝。遇到该情况交管理/实施人员按接口能力处理，不要伪造正金额退款。

### 8.2 整单作废

**前提**：有 POS 作废权限；销售尚未作废，原销售班次尚未交班，无已完成退货记录。赊账销售的客户若已有任何有效客户还款，因为还款未分配到销售单，系统拒绝直接作废该笔赊账销售。

**入口**：原销售记录 → “作废”。

**步骤**：核对需要撤销的是整单，填写必填作废原因；确认原货品和款项处理方式后提交。

**成功结果**：POS 销售及付款记录标记为已作废，关联出库单取消，库存按原扣减明细回补，报表单列作废金额。此操作不会调用微信、支付宝或银行卡通道退款。

**异常处理**：已交班、已有退货或已有客户还款时，不可直接作废。交班后的业务退回应按退货处理；已经还款的赊账单交管理人员核对退款/冲减，不要通过重开班次绕过结算核对。作废请求结果不确定时先查原销售状态；已作废不得再次扣/退库存。

## 9. 打印销售单与补打

**前提**：原销售已成功，具有销售查看权限；现场使用支持打印页面的环境，已选择适合的打印配置、纸型和打印机。

**入口**：结账前“自动打印销售单”及“打印配置”；成功后“打印销售单”；历史记录“打印”；班次区域与交班记录的“打印”。

**步骤**：选择配置，打开打印页面，检查销售单号、客户、数量、金额和页式，再在浏览器/系统打印界面确认设备及纸张。历史补打始终从原销售或原班次发起。

**成功结果**：前端 HTML 模式生成销售单页面并发起浏览器打印；后端模式打开服务端生成的销售或班次打印页面。系统记录打印来源和份次，可用于追溯发起过的打印操作。

**异常处理**：允许浏览器弹窗，核对登录、打印配置与纸型，必要时从原单手动补打。后台模式仍是打印页面，不会自动安装硬件驱动。非浏览器 PDA 环境能否打开页面和出纸需现场验证。打印日志、份次增加或“打印已发起”都不能证明已经物理出纸；打印日志保存失败时先检查实际出纸情况，避免盲目重复打印。

## 10. 交班、重开与销售报表

### 10.1 交班

**前提**：当前班次属于本人且进行中；结果不确定的销售、退货和还款已核对，现金与各支付渠道已实际清点。

**入口**：“当前班次” → “现金实点金额”及各支付方式“实点” → “交班”。

**步骤**：

1. 刷新班次，核对完成单、作废、退货、净销售、赊账及客户还款。
2. 输入现金实点总金额（含开班备用金）；逐一核对支付方式行的实点金额。现金支付方式行是现金交易净额，**不含备用金**，应与“现金实点总金额 − 备用金”一致。
3. 核对差额，按门店交接要求记录原因并交主管复核，再确认交班。页面输入框可能默认应收值，留空也会回填应收，不能据此认为系统替你完成实际盘点。
4. 在“交班记录”核对已交班状态，打印或导出交班结果。

**成功结果**：班次保存销售、退货和各支付方式的交班汇总、实点及差额。现金应点 = 备用金 + 有效现金销售（已扣找零）− 现金退款 + 现金客户还款；现金差额 = 现金实点 − 现金应点。

**异常处理**：差额非零可记录，但必须按门店制度核实，不应把金额改成应收以消除差额。提示只能交接本人班次时，由原收银员操作。交班后不能再在该班次新增销售；接班人员使用自己的账号开班。

### 10.2 主管重开

**前提**：班次已交班，主管有 POS 销售单修改权限；该班次原收银员在该仓库没有其他进行中班次。

**入口**：“交班记录” → “重开”。

**步骤**：核对班次与重开事由，确认后操作；当前 PDA 会记录带时间的重开原因，接口可提交具体原因。重开后由该班次原收银员继续业务，再重新交班。

**成功结果**：状态变为已重开，保留重开次数、人员与原因；再次交班重新汇总该班次业务。

**异常处理**：已有其他进行中班次、不是已交班状态或没有权限时，先处理班次冲突或交主管核查。主管重开不会把班次转移给主管本人。

### 10.3 报表与数据对账

**前提**：有销售查看权限，当前绑定仓库正确。

**入口**：首页 → “POS销售报表”或“POS数据对账”；POS 收银页也提供销售历史、统计和交班记录。

**步骤**：在报表选择“今日”“月度”或“时间段”，核对日期后刷新；查看销售、退货、作废、净销售、支付方式和商品/货主统计。使用“导出统计”“导出明细”保存 Excel，需要排查业务一致性时进入“POS数据对账”查看具体差异。

**成功结果**：查询或导出当前仓库、所选日期范围的数据。净销售以有效销售扣退货计算；客户还款为单列资金项目，不作为新销售额。跨日退货、跨班次还款按实际业务发生时间与处理班次归集，不能用某一天新销售总额直接推算现金余额。

**异常处理**：先检查日期、仓库和权限。对账提示差异时保留销售单号、退货/还款单号、日期范围和差异项目，交仓管或实施人员核查；不要直接修改后台只读销售流水。页面对账正常只说明其覆盖的系统数据检查未发现差异，不替代支付通道、现金和实物盘点。

## 11. 常见错误速查与培训检查表

| 现象 | 处理顺序 |
| --- | --- |
| 当前用户未绑定仓库／POS 仓库与授权范围不一致 | 暂停交易，管理员核对绑定仓库、角色范围及权限 |
| 未开班／已有进行中班次 | 刷新当前班次，使用本人班次；交接时由原收银员先交班 |
| 客户不存在／找不到客户 | 核对本仓库 POS 客户、启用状态及客户编号 |
| 商品不存在、无货或可售库存不足 | 核对商品和有效标识、拣货区库存；必要时交仓管补货 |
| 成交价或金额校验失败 | 核对基本数量、四位成交价、行金额及价格规则 |
| 支付明细合计不等于应收 | 检查每行抵扣，现金实收/找零与赊账零实收 |
| 库存繁忙、稍后重试 | 按系统等待提示，保留原销售请求；先查原结果再恢复 |
| 小票号已存在／原请求内容不一致 | 查原销售记录，禁止仅换单号或请求标识重复成交 |
| 已成交但无小票或未出纸 | 查原销售历史，从原单补打，不重新结账 |
| 还款结果待确认 | 回原账号、仓库和客户，查记录或恢复原请求；不重新收钱 |
| 退货/作废失败 | 查原销售状态、已退数量、班次及已有客户还款，按原因处理 |

培训验收应在隔离的测试环境、使用合成商品和客户记录完成，并记录实际结果：

- 能核对仓库与本人账号，开班、查班次并正确交班。
- 能区分包装数量与基本数量，核对新旧箱码对应箱规。
- 能完成现结、现金找零、拆分支付、赊账及客户还款。
- 能解释累计欠款与单笔赊账的区别，并处理还款结果不确定的情况。
- 能按原行金额处理部分退货，说明已还款赊销单不能直接作废的原因。
- 能在打印失败后从原单补打，核对现金实点总额与不含备用金的现金支付方式行。

本次文档更新没有运行数据库测试，没有操作业务数据库，也没有实施上述现场培训验收；本表是使用与验收步骤，不是通过记录。

## 附录 A：接口与数据契约

实施方使用配置好的服务地址；示例仅展示相对路径，不包含环境地址或真实账号。PDA 登录使用 `POST /api/token/`，需要登录的 POS JSON 请求使用授权头中的访问令牌。不要把访问令牌写进工单、文档或普通打印链接；打印页面按现有短期打印票据机制访问。

### A.1 主要入口

| 功能 | 接口 |
| --- | --- |
| 商品 | `GET /api/pos/products/?barcode=示例条码`；`?search=示例商品&page=1&page_size=20&zone_type=1` |
| POS 客户查询/新增 | `GET/POST /api/pos/customers/` |
| POS 客户详情/更新 | `GET/PATCH /api/pos/customers/{id}/` |
| 当前班次、开班 | `GET /api/pos/shifts/current/`；`POST /api/pos/shifts/open/` |
| 结账 | `POST /api/pos/checkout/` |
| 销售查询、详情、小票 | `GET /api/pos/sales/`；`/sales/{id}/`；`/sales/{id}/receipt/` |
| 作废 | `POST /api/pos/sales/{id}/void/`，必填 `reason` |
| 退货列表/新建、详情 | `GET/POST /api/pos/returns/`；`GET /api/pos/returns/{id}/` |
| 客户欠款、还款列表/新建 | `GET /api/pos/customer-debts/{customer_id}/`；`GET/POST /api/pos/repayments/` |
| 班次列表/详情 | `GET /api/pos/shifts/`；`GET /api/pos/shifts/{id}/` |
| 交班、重开 | `POST /api/pos/shifts/{id}/close/`；`POST /api/pos/shifts/{id}/reopen/` |
| 统计、对账 | `GET /api/pos/stats/`；`GET /api/pos/accuracy/` |
| 打印/前端打印日志 | `GET /api/pos/sales/{id}/print/`；`POST /api/pos/sales/{id}/print-log/` |
| 班次打印 | `GET /api/pos/shifts/{id}/print/` |
| Excel 导出 | `GET /api/pos/sales/export/`、`/stats/export/`、`/shifts/export/`、`/shifts/{id}/export/`，均位于 `/api/pos/` 下 |

`pos.add_possale` 控制收银、商品和 POS 客户接口；`pos.view_possale` 控制查询、统计和打印；退货提交同时要求 `pos.add_posreturn` 与 `pos.add_posrefund`；还款提交要求 `pos.add_poscustomerrepayment` 或 `pos.add_possale`；作废与重开要求 `pos.change_possale`。页面加载所需的查看权限应一并配置。

### A.2 客户和库存范围

`customer_id` 现指 `PosCustomer.id`，仅接受当前绑定仓库启用的 POS 客户。不能继续传货主基础资料 `Customer.id`，也不能以旧基础客户 ID 调用欠款与还款接口。POS 客户创建时仓库取当前用户，客户端不能通过 `warehouse_id` 变更仓库；未填写编号时自动生成，同仓编号唯一。

销售单使用 `pos_customer` 保存本次选择；历史 `selected_customer` 为兼容字段。各货主出库单始终使用对应货主下 `code=CASH` 的基础散客客户，不存在时创建。客户关联与订单拆分不能混用。

商品结果包含 `id`、`owner_id`、`code`、`sku`、`name`、`spec`、条码、`base_unit`、`price`、`min_price`、`max_discount`、`available_qty`、`unit_options`。包装选项包含单位与 `multiplier`；调用方必须按命中标识对应的包装快照换算基本数量。

商品查询可用 `zone_type`，结账对应使用 `stock_zone_type`；当前 PDA 两者均为 `1`（拣货区）。直接接口未传库区范围时按绑定仓库汇总/扣减可用库存。调用方应保持查询和扣减范围一致，不能用全仓库存展示值代替拣货区可售值。

### A.3 结账示例

以下编号均为合成示例，必须由测试环境实际准备的记录替换；不是可直接用于生产的请求。

```json
{
  "customer_id": 2001,
  "src_bill_no": "DEMO-POS-001",
  "idempotency_key": "demo-sale-request-001",
  "stock_zone_type": 1,
  "remark": "培训示例",
  "payments": [
    {"method": "CASH", "amount": "20.00", "amount_received": "30.00"},
    {"method": "WECHAT", "amount": "50.00", "amount_received": "50.00"},
    {"method": "CREDIT", "amount": "30.00", "amount_received": "0.00"}
  ],
  "items": [
    {"product_id": 101, "qty": "2.000", "price": "50.0000", "amount": "100.00"}
  ]
}
```

单一支付使用 `payment`，拆分支付使用非空 `payments`，调用方应只传适用的一种。方式枚举为 `CASH`、`WECHAT`、`ALIPAY`、`BANK_CARD`、`CREDIT`、`OTHER`。结账 `items[].qty` 最多三位小数且大于零，`price` 四位，显式 `amount` 两位且不得为负；金额为零时必须匹配零单价。非空拆分明细每行金额至少 0.01；全赠品单应使用单一支付，不构造零金额拆分明细。

成功响应为 HTTP `201`，包含 `sale`、`payment`、`orders`、`order_count`、`src_bill_no` 和 `receipt`。多个付款明细时汇总方式可能为 `OTHER`、参考号为 `MULTI`，明细才是拆分收款的依据。同一笔结账恢复须使用相同 `idempotency_key` 和相同业务内容；已存在的小票号会被拒绝，不能用重建小票绕过重复检查。库存并发重试耗尽时可能返回 HTTP `409`，含 `code`、`retryable` 与 `Retry-After`，实施方应保留原请求身份。

### A.4 还款、退货和班次字段

- 还款提交 `customer_id`、非赊账 `method`、两位小数 `amount`、可选 `reference_no`/`remark`，并提供稳定 `idempotency_key`。兼容路径可使用参考号生成请求身份，但新客户端应显式传请求标识；两者都缺失会拒绝。相同请求重放返回原还款及原审计的 `debt_before`、`debt_after`；查询最新欠款应另读欠款接口。
- 退货提交 `sale_id`、必填 `reason`、`lines[{sale_line_id, qty}]` 和 `refunds[{method, amount, reference_no}]`，应使用稳定 `idempotency_key`。后端有原键重放保护，但当前 PDA 退货按钮不会持久恢复上一次提交键。详情提供 `returned_qty`、`returnable_qty`、`returned_amount`、`returnable_amount`；赠品退货使用空 `refunds`。
- 开班提交 `opening_cash_amount` 和可选 `remark`；交班提交含备用金的 `actual_cash_amount`、按方式的 `payments[{method, actual_amount}]` 和可选 `remark`；重开必填 `reason`。现金方式行 `actual_amount` 不含备用金，不能直接复制现金总实点。
- 查询销售、退货、还款、班次均以用户绑定仓库过滤。收银权限校验另外执行显式角色范围与绑定仓库的一致性检查；不要把这些查询描述为跨仓经营查询。
