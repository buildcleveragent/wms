# WMS 发布级全面测试计划

## 1. 目标与结论规则

本轮对 Django 后端、Web Admin/Console、PDA、货主端、老板经营端、商城、POS、
支付、报表和计费执行发布级验收。测试只操作隔离环境，不修改业务实现，不使用生产
数据或生产支付凭据。

发布结论仅允许：

- `PASS`：所有强制门禁通过，无未处置 P0/P1。
- `CONDITIONAL PASS`：自动化通过，但真实设备、支付或恢复演练存在明确待完成项。
- `FAIL`：存在 P0/P1、核心构建失败、数据对账失败或强制测试未执行。

缺陷等级：P0 为跨租户泄露、库存/财务错误、超卖、支付错误或数据不可恢复；P1 为
核心流程不可用、生产客户端无法连接、权限绕过或主要门禁失败；P2 为局部功能、兼容
性或显著性能问题；P3 为展示、文案及低风险可维护性问题。

## 2. 环境与安全边界

- 记录 commit、工作树差异、Python、Node、MySQL、Redis、Docker 和浏览器版本。
- 仅使用 `127.0.0.1:33306` 的 MySQL 测试容器和唯一临时 `DB_TEST_NAME`；测试前
  校验 `APP_ENV=test`、主机、端口、库名和测试用户，禁止连接开发或生产库。
- 数据库测试先在全新 schema 串行执行；串行迁移成功后才允许 pytest-xdist 和并发
  专项。最终验证必须包含干净建库和真实迁移。
- 测试日志、截图和扫描报告必须脱敏，不记录密码、JWT、支付私钥或用户隐私。
- 当前没有 Browser 插件，前端渲染检查使用仓库 Playwright；临时脚本放 `/tmp`。

## 3. 测试矩阵

### 3.1 静态、迁移与供应链门禁

- Django `check`、生产 `check --deploy`、`makemigrations --check --dry-run`、迁移
  应用和反向一致性检查。
- lint ratchet、Black、isort、Ruff、Flake8、Bandit、依赖漏洞检查、Trivy 文件系统
  与镜像扫描。
- 依赖锁文件、Docker 构建上下文、客户端清单、重复路由和生产配置 fail-closed。

### 3.2 后端、数据库和业务闭环

- 串行执行全部 pytest 并生成覆盖率，门槛为总覆盖率不低于 70%。
- 独立执行库存、POS、商品标识、收货、上架、任务过账、出库审批、计费调度和支付
  退款并发测试，验证幂等、死锁、重试和整体回滚。
- 闭环覆盖：正式入库到上架、无单收货、批次/效期/序列号、出库审批到计费、短拣
  与取消、POS 开关班及退货、盘点/调整/移库/补货、FIFO/FEFO、计费到收款冲销、
  商城下单到支付退款售后评价。
- 每条链路后对账库存明细、汇总、流水、预占、任务、账单和报表事实。
- 在临时 schema 验证备份、恢复、业务数据清理和保留数据转移，恢复后比较表数、
  关键记录数、金额、库存和审计哈希。

### 3.3 权限、安全与接口

- 建立系统管理员、仓库管理员、仓库操作员、仓库老板、货主管理员、货主业务员、
  POS 收银员、商城买家和匿名用户的角色×接口×货主×仓库矩阵。
- 覆盖列表、详情、搜索、自动完成、Admin、导入导出、打印、直接对象 ID、批量操作
  和历史记录的水平/垂直越权；越权对象必须返回 403/404 且不泄露字段。
- 验证 JWT 限流、刷新旋转、旧令牌拉黑、改密吊销、退出、审计不可篡改、代理 IP、
  CORS、CSRF、HTTPS、上传限制和生产安全配置。
- 覆盖 Excel 公式、恶意类型、超大文件、非法 JSON、分页边界、重复幂等键、金额篡
  改、微信回调伪签名、过期、金额不一致和重放。

### 3.4 客户端与浏览器

- `wmspda`：单测、H5 构建、现有 Playwright E2E；登录、扫码、收货、上架、拣货、
  复核、POS、断网恢复和令牌刷新。
- `wmsownersale`：页面契约、单测、H5/微信构建；选仓、客户、购物车、开单、审批、
  库存、报表和账单。
- `sales-miniapp`：release gate、H5/微信构建；目录、搜索、购物车、多包裹、支付、
  退款、售后、地址和评价。
- `wmsbossbilling`：登录、范围筛选、驾驶舱、库存、预警和计费；缺少独立依赖清单或
  可重复构建时记为发布阻塞，不借用其他客户端工具链伪造通过。
- Web Admin/Console：登录、权限菜单、Dashboard、任务操作、导入导出和响应式布局。
- 视口至少覆盖桌面 `1440x900`、手机 `390x844`、PDA `720x1280`；检查页面身份、
  非空渲染、框架错误层、控制台、主要交互、遮挡、滚动和错误状态。

### 3.5 性能、恢复与外部环境

- 50 个持续并发用户运行 30 分钟，100 并发峰值运行 5 分钟。
- 关键查询 p95 不高于 800 ms；库存、下单、审批、过账和支付写接口 p95 不高于
  1.5 s；非预期错误率低于 1%；不得出现超卖、重复过账、死锁遗留或对账差异。
- 记录吞吐、CPU、内存、数据库连接和慢查询趋势。
- 故障注入覆盖数据库连接中断、重复调度、服务重启、支付超时、回调重放和部分写入
  失败。
- 预发布阶段验证至少一台主力和一台备用 PDA、一维码/GS1、连续/重复/破损码、可用
  的 RFID/NFC、蓝牙标签/小票打印和断线重连。
- 微信支付使用测试商户或受控小额交易验证成功、取消、超时查询、通知验签、重放、
  退款和对账。默认恢复目标为 RPO 不高于 24 小时、RTO 不高于 60 分钟。

## 4. 重点回归风险

必须重新验证商品详情匿名读取、Admin 多租户范围、任务/库存跨货主关系、客户端 API
地址、`release_to_pick`、配送单价格、过账失败审计回滚以及当前 lint 状态。发现问题
只进入报告，不在本轮自动修改业务代码。

## 5. 证据与报告

报告按模块记录环境、命令、用例数、通过/失败/阻塞/跳过、耗时和证据索引。每个缺陷
包含等级、影响范围、最小复现、预期/实际、日志或截图、相关模块和建议回归集合。
数据库建库、设备、凭据或预发布环境缺失必须记为 `BLOCKED`，不能算通过。
