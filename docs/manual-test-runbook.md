# WMS 全系统手工测试执行手册

> 适用范围：Web Admin/Console、`wmspda`、`wmsownersale`、`wmsbossbilling`、POS、
> `sales-miniapp`、业务 API、真实设备、微信支付及备份恢复。  
> 配套用例库：`docs/manual-test-cases.csv`。本文与 CSV 必须使用同一版本。

## 1. 使用方法

1. 只在隔离的非生产环境执行。先填写版本、数据库、客户端包和设备信息。
2. 按 P0、P1、P2、P3 优先级执行；同一优先级内按链条 `C01` 至 `C28` 执行。
3. CSV 中的“前置用例ID”通过后才能执行当前用例；多个前置用例使用 `|` 分隔。
4. 每次操作记录单号、任务号、货主、仓库、执行账号和时间；证据文件名以用例 ID 开头。
5. 结果只允许填写：`通过`、`失败`、`阻塞`、`不适用`。未执行时保持空白；设备或外部服务不可用必须填“阻塞”，不能填“通过”。
6. 写操作必须同时核对页面结果、业务状态、库存/流水/账务结果；失败用例必须确认没有残留副作用。
7. 发现缺陷后停止依赖该结果的后续链条，记录缺陷 ID，修复后重跑失败用例及其下游链条。

## 3. 准入条件与安全边界

- 已部署冻结的候选版本，`/healthz/live` 和 `/healthz/ready` 均正常。
- 数据库迁移已在同构测试库执行；测试库可恢复，且不是开发或生产业务库。
- 所有测试账号、货主、仓库、打印设备和测试商户已由负责人授权。
- 真实微信支付只使用获批准的测试商户或可立即原路退款的低额交易。
- 灾备、故障注入、服务重启和并发压测只在隔离环境执行。
- 不在截图、CSV、日志附件中保存密码、完整 JWT、微信密钥、证书私钥或个人敏感数据。
- 如基础数据不满足前置条件，先执行 `C01-C03`，不要直接修改库存明细、库存汇总、账单总额或支付状态。

### 4.3 计费、POS 和商城

- 为 OWN-A/WH-A 配置有效仓储费和作业费规则、服务合同、税率及测试账期。
- 准备账期内至少一条库存快照和已过账入/出库事件，另准备空账期、重叠账期和跨币种负例数据。
- POS 准备普通客户、赊销客户、最低价/最大折扣限制、现金和组合支付配置、可用打印机。
- 商城准备两个货主的上架商品、分类、Banner、地址、优惠券、积分、可支付订单和可评价已完成订单。

## 5. 状态与数据判定口径

### 5.1 任务状态

- 任务头：`RESERVED` 冻结预订 → `READY` 待发布 → `RELEASED` 已发布 →
  `IN_PROGRESS` 执行中 → `COMPLETED` 已完成；取消为 `CANCELLED`。
- 审核：`NOT_READY` → `PENDING` → `APPROVED/REJECTED`，盘点复盘可为 `NEED_RECOUNT`。
- 过账：`NOT_READY` → `PENDING` → `POSTED`；失败为 `FAILED`，盘点复盘可为 `NEED_RECOUNT`。
- 同一任务必须能从 `TaskStatusLog`、`TaskScanLog`、`TaskAssignment` 追溯执行人、扫描和状态变化。

### 5.2 入出库订单

- 入库提交：`DRAFT → SUBMITTED`；审核依次为 `OWNER_PENDING → OWNER_APPROVED/WHS_PENDING → WHS_APPROVED`，驳回或取消进入对应终态。
- 出库提交：`DRAFT → SUBMITTED`；审核依次为 `OWNER_PENDING → OWNER_APPROVED/WHS_PENDING → WHS_APPROVED`，驳回/取消为 `OWNER_REJECTED/WHS_REJECTED/CANCELLED`。
- 正式入库只有全部兄弟上架任务过账后才能关闭；正式出库在发运完成后关闭。

### 5.3 库存恒等式

- `可用数量 = 现存数量 - 分配数量`，任何阶段不得无业务理由为负。
- 收货增加收货/暂存库存；上架必须形成来源与目标成对流水且总量不变。
- 审核出库冻结分配量；拣货/发运过账减少现存量并释放分配量。
- 移库和补货必须形成数量相等、方向相反的成对流水。
- 盘盈、盘亏和调整分别形成明确类型流水；零差异盘点不应生成数量流水。
- `InventoryDetail`、`InventorySummary`、`InventoryTransaction` 和业务源单必须一致。

### 5.4 账务、POS、商城

- 账期：`OPEN → CLOSED → INVOICED`；锁账前必须通过 readiness/preview，解锁后才能修改受保护字段。
- 账单小计、税额、价税合计必须等于明细汇总；收款后回款状态和应收余额同步。
- POS 销售成功为 `COMPLETED`，撤销为 `VOIDED`；班次销售、退货、退款、还款和支付方式汇总必须可勾稽。
- 商城支付：`CREATED → PREPAY → PAID`，关闭为 `CLOSED`，退款过程为 `REFUNDING → REFUNDED`；退款记录为 `CREATED/PROCESSING → SUCCESS`，异常不得伪装成功。

## 6. 通用测试预言

每条写操作按以下顺序核对：

1. 页面/API 明确反馈成功或可理解的拒绝原因。
2. 刷新后状态保持，不依赖前端临时状态。
3. 源单、任务、分配/扫描/审核/过账日志均能互相追溯。
4. 库存明细、汇总、流水和报表数值一致。
5. 涉及金额时核对原价、调整、应付、实付、退款、税额和回款。
6. 重放同一幂等请求不重复建单、扣库存、计费、支付或退款。
7. 失败、超时、断网和权限拒绝后无半成品、无重复流水、无跨范围数据泄漏。

## 9. Admin 对象检查规则

每个已注册对象至少执行 CSV 中对应资源族的用例：

- 可维护主数据：列表、搜索、筛选、分页、新建、必填/唯一性、编辑、停用、被引用删除保护、范围过滤和审计字段。
- 业务单据：列表、状态筛选、详情、允许的领域动作、非法状态动作、批量动作、导出和来源追溯。
- 只读流水/日志/快照：列表、筛选、详情、不可新增/编辑/删除、范围和敏感字段检查。
- 高风险动作禁止通过直接编辑状态字段完成，必须使用审核、发布、过账、锁账、开票、撤销或退款等领域动作。

## 10. 真实设备、浏览器和外部服务

### 10.1 浏览器

- Chrome、Edge 当前稳定版：登录、菜单、列表、固定表头、横向滚动、表单、日期、筛选、分页、导出和返回导航。
- 1366×768 与 1920×1080：关键按钮不得被遮挡；缩放 80%、100%、125% 可操作。
- 所有 P0 页面检查控制台无未处理 JavaScript 错误，刷新和后退不重复提交。

### 10.2 Android PDA

- 使用硬件扫码头和摄像头分别扫描商品码、包装码、库位码和任务码。
- 测试短按、长按、连续扫码、重复码、错误码、无网络扫码和恢复后提交。
- RFID/NFC 插件：设备支持时验证加载、读取、无权限、硬件关闭及不支持提示。
- 至少完成一条真实入库、一条出库、一条盘点/移库和一条 POS 链路。

### 10.3 打印设备

- 蓝牙小票、标签打印机和出库单打印分别测试首次连接、断连、重连、缺纸、重复打印、份数和日志。
- 照片证据同时包含打印结果和页面业务单号；测试条码需回扫验证。

### 10.4 微信

- 使用两个不同买家验证绑定范围；完成一次低额支付、一次支付后原路退款和一次超时未支付关闭。
- 保存脱敏的商户订单号、微信交易号末四位、金额、时间和回调结果。
- 重放回调只能验证幂等，不得伪造或绕过签名在真实商户环境写入成功状态。

## 11. 非功能与灾备

### 11.1 临时性能目标

| 场景 | 目标 |
| --- | --- |
| 登录、首页首屏 | P95 < 2 秒 |
| 常用列表筛选 | P95 < 3 秒 |
| PDA 扫码提交 | P95 < 1 秒 |
| POS 结账 | P95 < 3 秒 |
| 小批量导出 | < 10 秒 |
| 中等批量导出 | < 60 秒 |

并发抽测：30 个 PDA 扫码/提交、20 个货主用户查询/下单/导出、5 个报表用户、5 个 POS 收银台。记录并发数、持续时间、成功率、P50/P95/P99、错误率、数据库锁等待和慢查询。

### 11.2 数据准确性

在应用虚拟环境和已确认的测试数据库中执行：

```bash
.venv/bin/python manage.py reconcile_data_accuracy --fail-on-issues
.venv/bin/python manage.py validate_sale_mini_data_accuracy --fail-on-issues --limit 20
```

库存、流水、账单、支付或退款存在不可解释差异时，本轮不得通过。

### 11.3 备份、恢复和回滚

1. 记录版本、迁移号、数据量和恢复点，完成数据库及媒体文件备份。
2. 恢复到新建隔离实例，核对表数量、关键行数、媒体文件和账号登录。
3. 在恢复实例运行迁移、健康检查、登录、库存只读查询及一条 P0 闭环。
4. 回滚到上一稳定镜像和兼容数据库状态，再执行相同冒烟。
5. 保存命令、耗时、校验值和负责人；任何步骤不得指向生产库。

## 12. 证据、缺陷和结果规则

### 12.1 证据最小集

- 正常写操作：操作前、成功提示、刷新后状态、关联单据/任务、库存或账务结果。
- 拒绝操作：输入或请求、错误提示、刷新后原状态、无新增流水/单据证明。
- 导入导出：原文件、预览、结果、导出文件；文件中个人信息必须脱敏。
- 硬件：设备型号、应用版本、操作照片/短视频、打印实物。
- 性能/灾备：配置、命令、开始结束时间、结果文件和负责人签字。

证据命名：`<用例ID>_<步骤>_<结果>_<时间>.<扩展名>`。

### 12.2 缺陷等级

- P0：无法登录/下单/过账，库存或账务错误，跨货主/跨仓泄漏，支付退款错误，迁移或恢复失败。
- P1：核心链路不可用或数据高风险错误，但存在受控人工规避。
- P2：低频功能、兼容性、提示或硬件异常。
- P3：文案、样式和不影响操作的视觉问题。

缺陷必须包含用例 ID、环境、账号角色、业务单号、完整复现步骤、期望/实际、证据、日志时间和修复版本。

## 13. 准出标准

- CSV 所有用例均有结论；任何“不适用”必须写明经负责人确认的原因。
- P0/P1 用例全部通过，且无未解决 P0/P1 缺陷。
- P2/P3 失败有缺陷、负责人、计划和经批准的上线处置。
- 二十八条链条的正常主路径通过；权限、库存、计费、POS、支付退款各至少一条失败无副作用用例通过。
- 数据准确性检查通过，库存、汇总、流水、账单、支付、退款无不可解释差异。
- Chrome、Edge、真实 Android PDA、扫码和打印证据完整；微信与灾备用例通过或被明确判定为发布阻塞。
- 备份恢复和回滚演练通过，最终由业务、财务、仓库、研发和运维给出 Go/No-Go。
